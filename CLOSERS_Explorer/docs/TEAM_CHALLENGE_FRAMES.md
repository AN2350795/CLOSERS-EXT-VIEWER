# 팀 챌린지 비주얼 프레임의 재생 데이터 분석

2026-10-19 로컬 클라이언트의 프레임 등록 테이블, 파티클 정의, 텍스처 애니메이션, PNG 및 CW.EXE를 정적으로 대조했다. 운영 `catalog.sqlite3`는 읽기 전용으로 열어 별도 작업 폴더에 복사했고, 게임 실행 파일이나 추출된 에셋은 변경하지 않았다. 아래 구현 차이는 조사 당시의 수정 전 재생기를 기준으로 기록했다. 이후 공통 재생기의 패스 순서를 수정했으며 적용 내용은 문서 끝에 기록한다.

## 확인한 결과

- 상·하의 빛이 좌·우로 이어지는 모습은 원본 텍스처 애니메이션에 들어 있다. 조사한 경로에서 네 변을 각각 별도 제어하는 전용 타이머나 팀 챌린지 ID 분기는 확인하지 못했다.
- 201~204번 모두 같은 10장·0.96초 테두리 애니메이션을 사용한다. 정적인 TOP/BOT 이미지 위에 이를 450×640 크기로 겹친다.
- 클라이언트의 텍스처 선택은 입자별 경과 시간과 프레임별 시간을 사용한다. 이 부분은 현재 브라우저의 기본 방식과 일치한다.
- **인게임과 수정 전 브라우저 사이에 기본·추가 발광 패스의 적용 순서 차이가 있었다.** 두 입자가 겹치는 동·은·금 프레임에서 먼저 그린 빛을 뒤의 기본 패스가 약화시키는 차이를 만든다.
- 실제 인게임 영상과 동일 시점의 픽셀을 비교한 결과는 아니다. 확인한 합성 순서 차이가 관찰된 차이 전부를 설명한다고 단정하지 않는다.
- **합성 순서 수정 후에도 보고된 좌·우 → 상·하의 타이밍 차이는 미해결이다.** 아래의 「순차 재생에 대한 추가 조사」는 이 피드백 이후 조사 결과다. 패스 순서 수정과 타이밍 문제 해결을 구분한다.

## 클라이언트 실행 파일에서 확인한 처리

조사 파일의 SHA-256은 `6d0ae9d4f41351e1c856be3a0b092f0a9f4999f367dbe7656d8247855bf90f8b`이다. 주소는 이 파일의 분석 근거이며 프로그램 코드에 하드코딩할 값이 아니다.

| 주소 | 확인한 처리 |
|---|---|
| `0x14095daf0` | 던전 로딩 UI 구성, TOP/BOT 및 연결 효과 적용 경로 |
| `0x141624760` | 애니메이션 한 장의 `m_TexName`, `m_fTime`, 선택적 TET/UV 정보 읽기 |
| `0x141627110` | `m_vecFrame`을 등록 순서대로 읽고 표시 시간을 합산 |
| `0x141622f40` | 시간에서 전체 주기의 정수 배수를 빼고 누적 표시 시간으로 텍스처 선택 |
| `0x1415b63bb`~`0x1415b63f2` | 입자 객체의 `+0x18` 시간으로 텍스처 및 선택적 UV 조회 |
| `0x1415b9f09`~`0x1415b9f53` | 해당 파티클 종류의 기본 렌더링 패스 실행 |
| `0x1415b9f58`~`0x1415b9fec` | 이중 합성 여부를 확인하고 추가 패스로 전체 렌더링을 다시 실행 |
| `0x1415b9f87`, `0x1415b9f91` | 추가 패스의 SRCALPHA / DESTALPHA 설정 |

텍스처 선택은 다음과 같은 일반적인 반복 재생이다.

```text
phase = 입자별 경과 시간 % 전체 프레임 시간
선택 이미지 = 누적 표시 시간이 phase보다 커지는 첫 이미지
```

현재 `web/particle-effects.js`도 입자별 `state.age`를 사용해 이 순서로 이미지를 선택한다. 이 시리즈에 좌·우용 별도 UV 영역도 등록되어 있지 않다. 따라서 별도의 네 변 이동 코드를 임의로 추가하거나 모든 장을 같은 시간으로 바꾸는 것은 원본 근거와 맞지 않는다.

## 확인된 브라우저 구현 차이: 이중 합성 순서

네 주 효과 모두 `m_EmitRate=2`, `m_iMaxParticleNum=2`, `m_LifeTime=999999`이고, `m_bDualBlending=TRUE`, `m_DrawCountDualBlending=3`이다. 동·은·금의 기본 합성은 ZERO / INVSRCCOLOR, 스페셜은 SRCALPHA / DESTALPHA다.

현재 재생기는 초당 2개·최대 2개로 입자를 만들고, 입자별 나이를 사용하므로 서로 다른 장면의 텍스처가 겹칠 수 있다. 다만 실제 클라이언트의 최초 생성 시각·프레임 단위 방출 오차까지 이번에 동등 검증한 것은 아니다.

두 입자 A/B가 있을 때 실행 파일에서 확인한 패스 순서는 다음과 같다.

```text
인게임: 기본 A → 기본 B → 발광 A×3 → 발광 B×3
수정 전: 기본 A → 발광 A×3 → 기본 B → 발광 B×3
```

수정 전 코드는 `ParticleEffects.draw()`의 `for (const state of particles)` 안에서 기본·추가 패스를 모두 실행했다. 인게임은 기본 패스의 입자 순회를 마친 다음 추가 패스의 입자 순회를 한다.

동·은·금의 기본 패스는 대략 `출력색 *= (1 - 텍스처색 × 기본색)`이므로, 현재 순서에서는 B의 기본 패스가 A의 발광까지 어둡게 만든다. 이 연산은 발광과 순서를 바꿔도 결과가 같은 연산이 아니다. 밝기가 변하면서 빛의 이동·연결 인상이 달라질 수 있다.

원본 `_00010`과 `_00001` 텍스처, 입자 나이 0.52초/0.02초, 불투명한 단색 바탕, 동일한 등록 색상·합성 인자·횟수로 RGB 계산을 비교했다. 서로 다른 것은 패스 순서뿐이다.

| 종류 | 차이가 생긴 픽셀 / 65,536 | 채널별 최대 차이 / 255 |
|---|---:|---:|
| 동 | 10,140 | 30 |
| 은 | 10,854 | 22 |
| 금 | 10,004 | 14 |

이는 합성 순서 차이를 분리한 CPU 수치 실험이다. 인게임 스크린샷·GPU 렌더링과의 픽셀 일치 결과로 해석하면 안 된다. 스페셜의 기본 패스는 다르므로 위 수치를 적용하지 않는다.

## 수정 시 우선순위

1. 파티클 효과 하나의 모든 입자를 기본 패스로 그린 다음, 같은 입자 상태를 추가 발광 패스로 다시 그리도록 순서를 맞춘다. 두 패스 사이에 난수를 다시 뽑거나 입자 나이를 바꾸면 안 된다.
2. 동일 시점·동일 배경에서 팀 챌린지 동·은·금·스페셜을 각각 비교한다. 정지 시점 비교와 재생 영상을 모두 확인한다.
3. 최초 입자 생성 시각, 생성 간격, 기존 입자와 새 입자의 위상 관계를 클라이언트의 실제 실행과 추가 대조한다. 겹쳐 보인다는 이유만으로 등록된 최대 입자 수를 1개로 줄이지 않는다.
4. 저장 영상 비교 시 편집기의 **자연스러운 순환**을 끈다. 이 옵션은 편집기의 교차 전환이며 인게임의 원래 주기 처리가 아니다.

## 로컬 증거 파일

프로젝트 루트의 `diagnostics/team-challenge-analysis/`에 다음 자료를 보관했다. 원본 게임 데이터와 생성 산출물이므로 Git에는 포함하지 않는다.

- `analyze.py`: 운영 DB를 복사하고 관련 정의를 읽는 분석 스크립트
- `definitions.json`: 네 프레임의 원시 행, 연결 파티클·애니메이션, 이미지 출처, 실행 파일 해시
- `texture-timeline.png`: 등록된 10장의 시간 순서와 원본 이미지
- `client.py`, `function-*.txt`: 정적 디스어셈블리 도구와 주소별 증거
- `compare_blending.py`, `blend-comparison.json`: 원본 텍스처로 패스 순서만 바꾼 수치 실험
- `blend-order-comparison.png`: 순서에 따른 RGB 결과 비교. 인게임 캡처가 아니다.

## 적용한 수정

공통 `ParticleEffects.draw()`에서 입자 상태·선택 이미지·변환 행렬을 한 번 준비하고, 전체 입자의 기본 패스 이후 전체 입자의 추가 발광 패스를 수행한다. 팀 챌린지 ID에 대한 예외 처리는 없다. 같은 이중 합성을 사용하는 다른 프레임·마크 효과에도 적용되며, 미리보기·PNG·APNG·WebP는 같은 렌더링 경로를 사용한다.

입자별 시간·난수·좌표·마스크·합성 인자·반복 횟수는 기존 값을 사용한다. 입자 수나 원본 애니메이션 시간을 조정해 움직임을 바꾸지 않는다. 저장한 조합 설정의 형식도 유지한다.

Chromium의 실제 WebGL 출력과 별도의 불투명 RGB 합성 수식을 비교하는 회귀 검증을 추가했다. 겹친 두 입자의 합성 순서, 서로 다른 나이에 선택되는 텍스처, 이중 합성이 없는 효과, 불투명도 0인 효과를 확인한다. 이 검증은 수정 전 코드에서 실패하고 수정 후 통과했다. 기존 단일 입자·마스크·UV·투명도·애니메이션 저장 검증도 함께 수행한다.

실제 에셋으로 불투명한 동일 배경에서 수정 전후 브라우저 출력을 비교했다. 1.02초·450×640 출력의 결과는 다음과 같다. 이는 두 브라우저 구현 사이의 차이이며 인게임 캡처와의 일치율이 아니다.

| 프레임 ID | 달라진 픽셀 / 288,000 | 채널별 최대 차이 / 255 |
|---|---:|---:|
| 201 | 43,647 | 29 |
| 202 | 48,282 | 21 |
| 203 | 40,693 | 14 |

이 네 표본의 0.1초 출력은 수정 전후 같았다. 비교한 218번 프레임과 201·203번 별도 마크는 0.1·1.02·1.14·1.62초에서 수정 전후 픽셀이 모두 같았다. 총 7개 표본에서 미지원 효과 경고가 없었고, 조합 설정을 복원한 1.14초 출력도 원래 출력과 같았다. 실제 201번 프레임으로 10장·10 FPS APNG를 저장하고 0·4·9번 장을 디코딩해 미리보기와 전체 RGBA 픽셀이 같은지 확인했다.

추가 증거는 같은 진단 폴더의 `render-validation.json`, `validated-frame-*.png`, `validated-mark-*.png`, `validated-frame-201.apng`에 보관한다.

## 순차 재생에 대한 추가 조사

사용자가 말한 현상은 좌·우의 이미지가 재생을 마치는 시점에 상·하가 이어지는 모습이다. 앞선 밝기 실험으로 이 현상의 원인을 확인한 것은 아니다. 이번에는 정의 중복, 생략된 방출 설정의 기본값, 입자 생성과 시간 갱신, 텍스처 애니메이션 이벤트 적용까지 조사 범위를 넓혔다.

### 조사 범위와 제외한 가설

운영 DB 복사본에서 다음 Lua 82개, 복원된 본문 합계 108,848,051바이트를 읽었다. 게임 스크립트를 실행하지 않고 본문과 리터럴 테이블을 조사했다.

| 범위 | 파일 수 | 결과 |

추가로 `TEX_ANIM_DATA.LUA`와 TEMP~TEMP4의 총 5개 애니메이션 파일, `FRAME_GROUP_TEMPLET.NTF`, 기존 두 프레임 NTF를 대조했다. 임시 애니메이션 파일에는 팀 챌린지 애니메이션이 없다. 따라서 현재 발견된 파일 집합에서 같은 이름이 나중에 다른 시간표로 덮어써진다는 근거는 없다.

`FRAME_TEMPLET.LUA`에 복원되는 프레임 목록은 53개이고 최대 ID는 105다. 201~204번이 등록된 NTF와 구분해야 하며, 이 Lua의 예전 항목을 현행 팀 챌린지 설정으로 사용하지 않았다. UI Lua의 상수에 이름이 등장한다는 것만으로 현재 프레임에 연결된 효과라고 판단하지 않았다.

### 방출과 시간 갱신에서 확인한 내용

아래 주소는 앞서 기록한 SHA-256의 실행 파일에 한정된다. 함수명은 심볼 복원 결과가 아니라 동작 설명이다. 정적 코드에서 확인한 일반 경로이며 실행 중 실제 UI 인스턴스의 상태를 측정한 결과는 아니다.

| 주소 | 확인한 동작 | 의미 |
|---|---|---|
| `0x1415d23ea`~`0x1415d2414` | 방출 시작·간격, 즉시 방출 수, 방출 간격 범위를 0으로 초기화 | 주 테두리에서 해당 필드를 생략했다고 별도의 순차 재생 설정이 켜지지는 않음 |
| `0x1415ba13e`~`0x1415ba16a` | 정의의 방출률 등을 시퀀스 인스턴스에 복사 | 원본의 방출 설정이 일반 생성 경로에 전달됨 |
| `0x1415c3a10`~`0x1415c3a34` | 비활성→활성 전환 시 즉시 방출 처리 호출 | 최초 방출은 즉시 방출 설정과 일반 방출을 구분 |
| `0x1415c36a9`~`0x1415c36f3` | 별도 방출 간격이 없으면 `방출률 × dt + 소수 잔여량`의 정수 부분만큼 생성 | `m_EmitRate=2`는 2초 간격이 아니라 초당 2개 |
| `0x1415c283a`~`0x1415c286a` | 현재 입자 수와 최대 수 비교 후 생성 제한 | 최대 2개에 도달하면 일반 경로에서 추가 생성하지 않음 |
| `0x1415bf0e0`의 초기화, `0x1415b551b`~`0x1415b553e` | 입자 시간을 0에서 시작하고 갱신마다 dt를 더함 | 텍스처 선택에 쓰는 `+0x18`은 입자별 경과 시간 |
| `0x1415a3fa0`~`0x1415a3fab` | 텍스처 애니메이션 이벤트가 준비된 애니메이션 포인터를 입자 `+0x4a8`에 대입 | 이 이벤트 자체는 입자 시간을 다른 입자와 맞추거나 재설정하지 않음 |
| `0x1415b63bb`~`0x1415b63f2` | 각 입자의 애니메이션 포인터와 경과 시간으로 이미지·UV 선택 | 모든 입자가 하나의 시퀀스 시계로 같은 장면을 선택하는 일반 구조는 아님 |
| `0x141664339`~`0x14166439b`, `0x1415ce445`~`0x1415ce4c7` | UI 효과 생성 시 방출률 등의 재정의 인자로 -1 전달, 해당 값은 재정의 생략 | 이 생성 지점에서 주 효과의 방출률을 다른 값으로 바꾼다는 근거 없음 |

주 테두리의 `m_EmitRate=2`, 최대 2개, 수명 999999초와 위 일반 경로를 함께 적용하면 입자는 대략 0.5초 간격으로 생겨 유지된다. 실제 프레임 간격과 초기 호출 조건에 따라 생성 시점은 프레임 단위로 달라질 수 있다. 브라우저가 연속 시간에서 계산하는 정확한 0.5초 간격과 게임의 모든 실행 프레임이 같다고 단정하지 않는다.

### 왜 두 입자의 겹침이 중요한가

단일 입자는 원본 10장을 0.96초 주기로 재생한다. 두 입자가 약 0.5초 차이로 생기면 거의 반 주기 차이의 이미지를 겹친다. 예를 들어 두 입자의 나이가 0.52초와 0.02초라면 각각 `_00010.png`와 `_00001.png`를 선택한다. 따라서 한 입자가 좌·우 쪽으로 넘어갈 때 다른 입자는 상·하 쪽을 표시할 수 있다.

이는 동시에 보이는 이유를 설명하는 **데이터와 일반 코드에 따른 예상**이다. 인게임에서 실제로 두 입자가 이 간격으로 그려지는지 확인했다는 뜻은 아니다. 현재 정적 조사만으로는 사용자 관찰과의 차이를 해소하지 못했다.

이름이 비슷한 `PE_UI_VISUAL_FRAME_TEAM_CHALLENGE_VISUAL_FRAME_*` 계열에는 최대 입자 1개인 설정도 있다. 하지만 해당 효과는 `PE_TEAM_CHALLENGE_VISUAL_FRAME_ONE_LINE`을 사용하며, 등록 테이블의 별도 마크 효과와 연결된다. 이를 사각 테두리의 대체 정의로 적용하거나 이름만 보고 최대 입자를 1개로 바꾸면 다른 요소의 데이터를 섞게 된다.

### 결론과 남은 확인

현재 조사한 등록 데이터와 일반 생성·갱신·렌더링 경로에서는 **좌·우의 종료를 기다렸다가 상·하를 시작시키는 전용 처리나 팀 챌린지 ID별 시간 분기를 발견하지 못했다.** 빛의 이어짐은 원본 이미지 시간표에 있으며, 복수 입자의 겹침이 그 인상을 바꿀 수 있다.

다만 실제 인게임과의 타이밍 차이 원인은 아직 확정하지 못했다. 등록값만으로 입자 수나 위상을 임의 변경하지 않았다. 다음으로 필요한 검증은 같은 프레임·같은 표시 화면의 인게임 연속 장면을 원본 10장 및 브라우저 출력과 대조하는 것이다. 시작 순간만 달라졌는지, 주기가 다른지, 실제로 한 위상만 보이는지를 구분해야 한다. 관찰한 화면이 던전 로딩인지 프레임 선택 미리보기인지도 이 대조에 포함해야 한다.

추가 원시 증거는 진단 폴더의 `audit_scope.py`, `scope-audit.json`, `extra-audit.json`, `parsed-frame_templet.json`, `parsed-dlg_character_info_skin_v3_frame.json` 및 주소별 디스어셈블리 파일에 보관한다. 이 절은 타이밍 수정 완료 보고가 아니라, 확인한 범위와 미확정 사항을 구분하는 조사 기록이다.

## 추가 추적: 같은 갱신에서 생성된 입자는 같은 위상으로 시작한다

앞 절의 약 0.5초 간격은 **작은 dt로 규칙적으로 갱신되는 조건**에서의 예상이다. 게임의 방출 구현이 임의의 갱신 간격에서도 정확히 0.5초 간격의 생성 시각을 복원한다는 뜻은 아니다. 이 조건을 분명히 하지 않고 브라우저와 게임의 타이밍 방식이 일치한다고 해석하면 안 된다.

### 실제로 더 확인한 실행 경로

- `0x140812636`~`0x140812667`: UI 전용 파티클 시스템을 만들고 시스템의 `+0x1c9` 플래그를 1로 설정한다.
- `0x1408126ac`~`0x140812898`: UI, UI_2, UI_3, SPINE_UI, UI_TEMP, UI_TEMP2 여섯 Lua를 로드 목록에 추가한다. 앞서 조사한 UI 파일 집합을 실제 로더에서도 확인했다.
- `0x1408128c8`~`0x1408128d4`: 위 시스템을 UI 관리자 `+0x148`에 연결한다. 프레임 `PicData::CreateParticleSeq`가 참조하는 시스템과 연결된다.
- `0x140808086`~`0x140808092` 및 `0x14080891b`~`0x14080892f`: UI 시스템 갱신 함수에 호출자가 받은 dt를 전달한다.
- `0x1415cd585`~`0x1415cd58e`: 시스템 갱신에서 각 시퀀스의 가상 함수 `+0x08`에 같은 dt를 전달한다. 가상 함수 테이블 `0x1425bcb50`의 두 번째 항목은 `0x1415c2fb0`이다.

전역 효과 제한을 적용하는 경로도 있다. `0x1415a6a10`은 옵션·상태에 따라 `0x1415a6930`으로 이동하며 최대 입자 수 등을 제한할 수 있다. 그러나 시스템 `+0x1c9`가 1이면 이 경로를 건너뛴다. 위 UI 시스템은 이 플래그가 1로 설정되므로, **이 전역 제한을 근거로 팀 챌린지 UI의 입자 수를 1로 줄여서는 안 된다.**

### 현재 재생기와 다른 방출 방식

게임의 일반 방출 경로는 다음 순서다.

```text
기존 입자들의 나이 += dt
이번 생성 수 = 정수 부분(방출률 × dt + 이전 잔여량)
이번 생성 수만큼 새 입자를 생성 — 각 입자의 초기 나이는 모두 0
```

`0x1415c36f0`~`0x1415c3701`의 반복문은 입자 생성 함수에 서로 다른 과거 생성 시각이나 나이를 전달하지 않는다. `0x1415c295f`~`0x1415c296c`의 일반 생성 호출을 거쳐 초기 나이가 0이 된다. 반면 현재 브라우저 `timeline()`은 `next += 1/rate`로 시각을 복원하며, 큰 시간 이동에서도 0.5초와 1.0초에 태어난 별개 입자를 만든다.

따라서 방출률 2, 최대 입자 2 조건에서 다음 두 결과가 가능하다.

| 갱신 조건 | 게임 코드에서 예상되는 두 입자의 나이 차 | 현재 브라우저의 나이 차 |
|---|---:|---:|
| 처음부터 60 FPS로 규칙적 갱신 | 약 0.5초 | 0.5초 |
| 첫 유효 갱신의 dt가 1초인 가정 | 0초 — 같은 호출에서 둘 다 생성 | 0.5초 |

이 표의 두 번째 행은 **가정을 넣은 재현 실험**이며, 인게임 로딩에서 실제로 dt=1초가 들어온 것을 측정한 결과가 아니다. 호출자의 dt 제한·초기화 조건과 실제 프레임의 생성 이력을 확인해야 원인으로 확정할 수 있다. 다만 「방출률이 2이므로 게임에서도 두 입자가 언제나 반 주기 차이」라는 가정은 성립하지 않는다는 구체적 근거다. 수명이 매우 길어 두 입자가 같은 위상으로 생성되면 이후에도 함께 재생할 수 있다.

진단 `emission_batches.py`는 정적으로 확인한 반복문을 float32로 분리 재현한다. 60 FPS 조건에서는 약 0.5초, 첫 1초 갱신 가정에서는 0초 차이가 나오는 것을 assertion으로 확인했다. 결과는 `emission-batches.json`이다. 앱 재생 코드는 이 실험 때문에 변경하지 않았다.

원본 텍스처와 동 프레임의 기본·발광 합성으로 만든 `phase-hypotheses.gif`는 왼쪽에 0.5초 차이, 오른쪽에 같은 위상의 두 입자를 보여 준다. 이는 위상 차이만 분리한 RGB 비교 자료이며 인게임 영상이나 게임 전체 렌더러의 재현 결과가 아니다. `compare_phase.py`로 다시 만들 수 있다.

이 비교에 대해 사용자는 **오른쪽 B가 실제 인게임에 더 가깝다**고 확인했다. 따라서 현재 재생기의 고정된 약 0.5초 위상 차이를 우선 조사 대상으로 삼을 관찰 근거가 생겼다. 다만 같은 화면은 한 입자 또는 두 입자의 동기화 등으로도 나타날 수 있으므로, 이 응답을 게임의 실제 입자 수나 동시 생성 경로가 확정됐다는 뜻으로 해석하지 않는다.

### CMF 밖의 Lua 확인

설치 폴더의 `CLIENT_CODE_0.LUA`~`CLIENT_CODE_3.LUA` 네 파일도 Lua 5.1 프로토타입 구조로 읽었다. 코드는 실행하지 않았다. 각 파일은 하나의 최상위 프로토타입이며 문자열 상수는 각각 61,217 / 59,524 / 59,523 / 59,521개다. `VERSION`, `CODE_TABLE`과 다수의 파일 이름이 확인된다. frame, particle, loading, emit, sequence, team_challenge 문자열을 검색했을 때 관련 항목은 `CM_TEAM_CHALLENGE.MP3` 하나였다. 별도의 프레임 시간표를 여기서 발견하지는 못했다. 이는 모든 명령의 의미를 분석했다는 주장이 아니다.

근거는 `client_lua_audit.py`, `client-lua-audit.json`에 보관한다. 추가 조사 결과는 「더 볼 데이터가 없다」가 아니라 **실행 중 생성 이력에 따라 정의값만으로 결정되지 않는 위상 차이가 생길 수 있고, 현 재생기가 그 조건을 표현하지 못한다**는 것이다. 이 조건이 사용자 관찰의 원인인지는 여전히 구분해서 검증해야 한다.
