# 원본 Glow/HDR와 뷰어 발광 번짐 비교

2026-11-01. 원본 후처리 DXBC 5개와 아바타 DXBC 4개, CW.EXE의 Glow 경로를 조사하고 **5단계 원본 흐림 비교**를 추가했다. 기본 번짐은 기존 방식이며 사용자가 비교 방식을 직접 선택한다.

## 뷰어에서 사용하기

**조명·재질 → 광택·발광 → 빛 번짐**을 켜고, **번짐 방식 → 5단계 · 원본 흐림 비교**를 선택한다. 켜진 발광 재질이 있는 모델에서 동작하며 방식과 강도를 저장한다. 기본값은 **기본 · 가벼운 번짐**이다.

비교 방식은 1/2~1/32 크기의 UNORM8 타깃에서 가로·세로 9샘플 흐림을 5단계로 수행한다. 첫 단계는 뷰어의 발광 입력을, 다음 단계는 직전 세로 결과를 읽는다. 계수는 조사한 초기값 1을 사용하고 가중치를 재정규화하지 않는다. 표면 렌더에서는 발광 가산을 잠시 제외하고 5개 결과를 합성하여 중복 발광을 방지한다. 강도 1일 때 조사한 모드 1의 RGB 합성 구조에 해당하며, 강도 슬라이더는 뷰어의 비교 배율이다.

기본 화면 알파는 유지한다. 원본의 전체 MRT1 알파·재질별 블렌딩·굴절·장면 파티클은 재현하지 않으며 기존 뷰어의 깊이·투명도 처리를 사용한다. 따라서 **인게임 bloom 재현 완료를 뜻하지 않는다.** 색감·선명도 탭의 색상 계산 선택도 자동 변경하지 않는다. 원본 형식 색상 계산을 끈 상태에서는 뷰어 색상 공간에서 비교한다.

발광만 보기에서는 기본 번짐을 사용하고, 광택 범위 확인에서는 번짐을 보류한다. 발광/번짐을 끄거나 기본 방식으로 돌아오면 기존 표면 표시를 복원한다. 아주 작은 렌더 영역(한 변 32px 미만)에서도 기존 번짐을 사용한다. 비교용 타깃은 처음 사용할 때 생성하고 뷰어 종료 시 해제한다. 흐림 패스가 늘어나므로 기본 방식보다 GPU 작업량이 많다.

현재 **빛 번짐**은 발광 부위를 확인하는 뷰어 기능이다. 게임의 빛 번짐 옵션을 그대로 구현한 것으로 간주할 수 없다. 또한 모델의 `_GLOW` 표면 보조광 텍스처는 이 화면 후처리 Glow와 구분한다.

## 원본 셰이더에서 확인한 식

`CW_ScreenQuad_Glow.PS.cso`는 `CBPerGlobal[6].x`의 모드를 확인한다. `p=CBPerGlobal[7].y`, `A=saturate((blur1+…+blur5)/5)`일 때 다음 RGBA 식이다.

- 모드 2: `saturate(A*p + base*(1-saturate(A*p)))`
- 다른 모드: `saturate(5*A + base)`

따라서 모든 모드에서 같은 강도를 곱하는 가산 합성으로 대체할 수 없다. 확인한 주 Glow 호출은 모드 1을 전달한다. 번짐 단계 수는 CPU에서 최대 5로 제한하지만 실제 실행 중 단계 수·계수 덮어쓰기와 다른 모드의 호출자는 아직 확인하지 않았다.

`CW_Blur_Horizon.PS.cso` / `CW_Blur_Vertical.PS.cso`는 `CBPerPostProcess[1..9]`의 X/Y 오프셋과 `[10..18]`의 X/Y 가중치를 각각 사용한다. 각 패스 출력에 포화 연산을 적용한다. 이어 조사한 CPU 생성식과 타깃 연결은 아래와 같다.

## 타깃·가중치·입력 연결 확인

`0x141574695`의 제수는 `2, 4, 8, 16, 32`이다. 가로·세로 타깃은 같은 크기이고, 나눗셈의 나머지는 버린다. 리소스 키 1은 화면 치수를 사용하고 키 2는 별도 기준 `390×730`을 사용한다. **리소스 키와 합성 모드는 서로 다른 입력**이다. 키 2라는 이유로 모드 2로 판정하지 않는다.

| 단계 | 화면 1920×1080 기준 | 리소스 키 2 기준 |
| --- | --- | --- |
| 0 | 960×540 | 195×365 |
| 1 | 480×270 | 97×182 |
| 2 | 240×135 | 48×91 |
| 3 | 120×67 | 24×45 |
| 4 | 60×33 | 12×22 |

`0x141570910~0x141570998`에서 `k=i-4`인 9개 샘플을 구성한다. **현재 가로 타깃 크기** W/H를 기준으로 X/Y 오프셋을 `(k/W, k/H)`로 계산한다. 입력 원본의 해상도를 기준으로 하지 않는다. 세로 패스는 같은 단계의 가로 결과를 읽는다. 다음 단계는 이전 단계의 세로 결과를 읽으므로, 독립된 5회 흐림과도 다르다.

실행 파일의 식을 실수 수식으로 재구성하면 다음과 같다. `s`는 +0x274에서 가져오는 계수이며, 아래 pi 상수는 원본 float32 `6.2831854820251465`이다.

```text
weight(k) = exp(-((k/s)^2)/(2*s*s)) / sqrt(float32(2*pi)*s*s)
```

일반적인 Gaussian으로 단순화하면서 **추가 `1/s`를 삭제하면 안 된다.** 생성 뒤 9개 가중치를 합계로 나누는 정규화는 이 경로에 없다. 초기화·정리 경로에서는 단계 수 5, s=1, 모드 0을 기록한다. 이것을 실행 중 항상 같은 값이라는 뜻으로 해석하지 않는다. s=1일 때 중심 가중치는 약 0.39894228, 양 끝은 약 0.0001338302이다. s=2에서는 가중치 합이 1을 넘으므로 임의로 정규화하면 밝기가 달라진다.

`0x1415707d6~0x141570803`에서 필터 0x15와 U/V/W 주소 모드 3인 샘플러 설명을 전달한다. `0x141615b30` → `0x14161c0a0`의 CreateSamplerState 연결을 대조하면 선형 필터·CLAMP이다. 타깃 포맷은 생성 설명의 28(UNORM8)을 따른다.

`0x14157082e`는 기본 입력 SRV +0x1a0을 잡고, **모드 1이면서 첫 단계**일 때 +0x1a8로 바꾼다. 주 Glow 호출은 `0x141572ffc`에서 모드 1을 넘기며, helper가 +0x278에 저장한다. 따라서 이 직접 경로의 첫 입력을 최종 기본색 이미지로 대체하면 달라진다. 이어 확인한 입력 타깃의 연결과 셰이더 출력은 아래와 같다.

## 첫 입력은 두 번째 렌더 타깃

타깃 객체 안에는 같은 슬롯 번호로 연결되는 다음 배열이 있다. 슬롯 번호를 `i`로 표시한다.

| 역할 | 객체 내부 위치 | 연결 근거 |
| --- | --- | --- |
| 일반 텍스처 | `+0x50+8*i` | `0x1416095c0`에서 CreateTexture2D |
| 읽기용 SRV | `+0x1a0+8*i` | `0x141609898`에서 같은 텍스처로 CreateShaderResourceView |
| 일반 RTV | `+0xe0+8*i` | `0x14160a3df`에서 같은 텍스처로 CreateRenderTargetView |
| MSAA 텍스처 / RTV | `+0x90+8*i` / `+0x120+8*i` | `0x141609c92`, `0x141609e5c` |

`0x1416090c5~0x1416090f9`는 샘플 수에 따라 일반/MSAA RTV 배열을 고르고 +0x21c의 개수로 OMSetRenderTargets에 전달한다. 그러므로 **SRV +0x1a8은 슬롯 1, 즉 픽셀 셰이더의 SV_Target1에 대응한다.** 단순히 이름이 비슷한 다른 텍스처를 연결한 해석이 아니다.

일반/MSAA clear 경로도 각 RTV를 순회한다. MSAA일 때는 `0x141608fb3~0x141608feb`가 모든 슬롯을 포맷 28로 일반 텍스처에 ResolveSubresource한다. 장면 그리기 뒤의 `0x140d71110~0x140d7114e`는 같은 메인 타깃을 마무리한 뒤 Glow 포함 후처리를 호출한다. 다른 슬롯의 결과가 무조건 슬롯 0으로 복사된다고 해석하지 않는다.

## 아바타가 MRT1에 기록하는 값

`CW_Default.PS.cso`, `CW_CartoonLight.PS.cso`, `CW_Add_CartoonLight.PS.cso`의 일반 경로를 대조했다. 이미 음영·알파 처리가 끝난 표면값을 S, 다음 발광값을 E라고 하면 다음과 같다.

```text
E = sampleLevel(t12, originalUV, 0) * CB5[16] * CB5[17].x * CB5[17].y
SV_Target0 = S
SV_Target1 = E
단, E.rgb가 모두 정확히 0이면:
    SV_Target1 = (0, 0, 0, E.a > 0 ? S.a : 1)
```

RGB와 알파 모두 발광 텍스처·색·두 강도 성분의 영향을 받는다. 이 **셰이더 출력 시점**에는 발광 RGB에 알파를 한 번 더 곱하지 않는다. 이후 블렌딩·깊이·UNORM 저장은 별도다. 검은 출력이라고 알파도 항상 0인 것은 아니다.

또한 표면 출력 S에 E를 직접 더하는 명령은 이 일반 경로에 없다. 뷰어의 기본 방식은 표면에 발광을 더하고 별도 발광 마스크도 생성한다. 따라서 흐림 패스만 5단계로 바꾸면 기본색에 이미 더한 발광이 중복될 수 있다. 새 비교 방식에서는 표면을 그리는 동안 발광 가산만 제외하고 마스크를 그리기 전에 원래 켜짐 값을 복원한다. 렌더 오류가 나도 복원하며 사용자 설정은 수정하지 않는다.

`CW_NoLight.PS.cso`에는 예외가 있다. `CB5[23].x>0`인 굴절 경로에서는 투영 좌표로 t8/t9를 읽고 **t9 샘플을 SV_Target1에 기록**한다. 이 분기가 아닐 때에는 t12 기반 발광을 기록하지만 알파 계산 시점까지 위 셰이더들과 동일하다고 간주하지 않는다. 즉 MRT1 전체를 XET 발광 텍스처 목록만으로 설명할 수 없다. 다른 장면 셰이더·파티클의 기여도 별도 조사 대상이다.

진단 코드 `avatar_mrt()`는 일반 경로의 표면/발광 출력과 검은 RGB의 알파 분기만 재구성한다. 블렌딩·양자화나 굴절 경로를 재현하지 않으며, 보고서의 `first_input.example`은 실제 프레임을 읽은 결과가 아니다.

## 알파 블렌딩·깊이 확인 범위

`0x14161bed0`의 블렌드 상태 생성 경로는 조건에 따라 `0x14161bf25`에서 IndependentBlendEnable을 켜고, 타깃 1에는 타깃 0의 켜짐·소스/대상 계수를 복사한다. 타깃 2에는 별도 SRC_ALPHA / INV_SRC_ALPHA를 지정한 뒤 `0x14161bf71`에서 CreateBlendState를 호출한다. 이는 **타깃마다 다른 블렌딩을 사용하는 경로가 존재한다는 근거**이다. 모든 아바타 그리기에서 이 분기가 선택되거나 같은 계수가 적용된다고 단정하지 않는다.

현재 비교 방식은 뷰어의 기존 재질 깊이 검사·알파 테스트를 유지한다. 불투명 아바타 메시가 발광을 가리면 번짐도 가려지는지 GPU로 검사했다. 투명 메시 순서와 원본의 타깃별 알파 계산, 실시간 깊이 상태의 완전한 대응은 남아 있다.

`CW_GetBright.PS.cso`는 각 RGBA 채널에 `saturate((input-threshold)/(1-threshold))`를 적용한다. 임계값은 `CBPerPostProcess[19].x`이다. 보관된 구형 FX의 RGB 평균 기반 밝기 추출과 다르므로 최신 DXBC를 기준으로 삼는다. 이 셰이더가 현재 Glow의 입력 생성에 쓰이는지는 추가 확인이 필요하다.

`CW_HDR.PS.cso`는 원본 화면 RGB 합과 깊이 G를 이용해 UV를 `(0.5,0.6)` 방향으로 이동시킨다. 이동량은 `depth.g * sum(source.rgb) * 0.02`이다. 이동한 좌표에서 원본을 다시 읽고 `factor=1-average(source.rgb)`를 계산한다. factor가 음수인 경우에만 minimum으로 바꾼다. 결과 RGB는 `source + bright * power * factor`이며 알파는 다시 읽은 원본값이다. power와 minimum은 `CBPerPostProcess[20].xy`이다. 이 식의 존재만으로 게임 실행 중 HDR이 켜져 있다고 판정하지 않는다.


기존 출력 경로 근거 42곳과 추가 Glow·타깃·블렌딩 근거 **51곳**, 셰이더 **9개** 지문을 검사한다. 원본이 다르거나 중복 출처의 내용이 다르면 검증을 중단한다. 감사 도구는 셰이더·게임을 실행하거나 원본을 수정하지 않는다. 로컬 진단 JSON과 디스어셈블 결과는 저장소에 포함하지 않는다.

`test_bloom_browser.py`는 각 단계의 GPU RGB를 독립된 픽셀 중심 bilinear·CLAMP·UNORM8 계산과 대조하고, 발광 중복·알파 유지·설정 전달·오류 후 상태 복원·MSAA·선명도/색상 보정 연계를 검사한다. 실제 트리니티 휠 의상과 날개에서도 번짐 표시를 확인했다. 이는 로컬 뷰어 검증이며 인게임 프레임 대조가 아니다.

보고서 `blur_path.examples`는 1920×1080을 진단 입력으로 사용한 타깃·오프셋·가중치·입력 연결 계획이다. 실제 게임 상태를 읽어 온 결과가 아니다. `--width` / `--height`로 진단 치수를 바꿀 수 있다. Python exp/sqrt로 재구성하므로 원본 float32 CRT와 비트 단위 일치를 보장하지 않는다. 0 크기 타깃이나 유효하지 않은 수치를 임의 보정하지 않고 거부한다. `test_bloom_reference.py`는 홀수 치수 버림·모드와 리소스 키 분리·비정규화·추가 역수 계수를 검사한다.
