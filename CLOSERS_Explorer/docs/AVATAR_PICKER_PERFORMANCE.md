# 아바타 목록과 썸네일 로딩 개선

2026-10-24 실제 `results`로 비교했다. 기준 코드는 `9cb2105`, 구현은 `3efd40a`와 `e916ac7`이다. 게임 원본과 기존 추출 파일은 수정하지 않았다.

## 같은 조건의 브라우저 측정

별도 8771 서버, 새 서버 프로세스와 새 Chrome headless 프로필을 사용했다. 화면 1512×1000, SwiftShader, 하피(ROGUE), 저장 상태 전체, 페이지당 20개, 기본 정렬로 같은 순서의 실제 UI 선택을 수행했다. OS 파일 캐시와 디스크 파생 캐시는 비우지 않았다. 아래는 각 시나리오의 1회 측정값이며 평균·백분위가 아니다.

단위는 초다. 목록 완료는 실제 카드 DOM의 `aria-busy=false`, 썸네일 완료는 현재 목록 영역에 보이는 세 카드의 이미지 디코딩 또는 아이콘 없음 안내 완료다. 썸네일 열은 목록 요청 시작부터의 전체 시간이다.

의상 1페이지의 처음 세 카드는 원래 아이콘이 없어 안내 완료를 측정한 값이다. 실제 이미지가 있는 의상 2페이지의 목록 완료 후 썸네일 추가 대기는 2.243→0.097초, 부위 목록은 2.078→0.064초였다. 화면 바깥 80px의 기존 지연 로딩 여유 영역은 유지했다.

목록 총수는 전후 모두 의상 470묶음, 부위 2,212개, 액세서리 1,455개, 눈동자 54개였다. 보이는 아이콘 출처도 전후 일치했다. 예: 의상 2페이지 154899/156506/156511, 부위 25748/25759/25764, 액세서리 26172/26173/26174, 눈동자 143313/346812. 두 회차 모두 브라우저 예외는 0이었다.

로컬 원시 자료: `diagnostics/picker-{before,after}-browser.json`. 실제 8765 서버 반영 후에도 같은 UI 시나리오를 다시 실행해 성공했다. 그 확인 회차는 첫 의상 2.486초, 의상 2페이지 썸네일까지 0.938초였으며 비교 표의 수치를 이 더 빠른 값으로 바꾸지는 않았다. 자료는 `diagnostics/picker-main-verified-browser.json`, `picker-main-verified.png`에 있다.

## 확인한 병목과 변경

아이콘 조회의 `category='images' AND name COLLATE NOCASE IN (...)`에서 SQLite가 분류 인덱스를 선택해 각 이름 묶음마다 이미지 분류를 스캔했다. 기존 `idx_entry_name_nocase`를 명시해 정확한 이름 검색을 사용하도록 했다. 구성 모델과 눈동자 이미지 조회에도 같은 원칙을 적용했다. 인덱스를 새로 만들거나 원본 데이터를 재분석할 필요는 없다.

`ModelGroups.browse()`와 `EyeAvatars.browse()`는 요청 하나에 Catalog 세션을 공유한다. 이름 원본 검사는 다음 요청에서 다시 수행한다. 기존 snapshot과 정의 캐시는 유지하고 목록 결과 전체를 새로 캐시하지 않았다. 따라서 필터·타입·페이지·저장 파일 존재 여부가 이전 결과에 고정되지 않는다.

| --- | ---: | ---: | ---: |
| 의상 최초 | 3→1 | 14,026→4,708 | 3.184→1.600초 |
| 의상 2페이지 | 2→1 | 9,350→4,691 | 1.700→0.281초 |
| 의상 재방문 | 2→1 | 9,350→4,691 | 1.480→0.158초 |
| 부위 | 2→1 | 9,370→4,711 | 1.536→0.156초 |
| 액세서리 | 2→1 | 9,370→4,711 | 1.483→0.131초 |

SQL 문장 수는 의상 최초 14개, 반복 13개로 유지된다. 줄인 것은 각 조회의 스캔 비용과 중복 이름 검사다. 최종 `refresh()` 2회 중 실제 원본 검사는 세션 시작의 1회이고 연결 등록 시 호출은 즉시 반환한다. 위 시간은 프로파일링 오버헤드를 포함하므로 브라우저 표와 혼합하지 않는다. 원시 자료는 `diagnostics/picker-{before,after}-profile.json`이다.

썸네일 `/api/media`는 `Catalog.get()`의 이름·중복 통계·이력 조회 대신 `get_resource()`를 사용한다. 이름 원본 검사 2회를 생략하면서 실제 이미지 원본 확인은 유지한다. 이미지 캐시 파일명은 출처 경로·순번·오프셋·크기·형식과 저장 파일 상태를 구분한다. HTTP는 `private, no-cache`와 ETag를 사용하며 원본 검증 이후에만 304를 반환한다. 저장 이미지 편집과 원본 변경이 오래된 HTTP 응답으로 가려지지 않는다. 기존 인증, Range 응답, 64 MiB 입력·32,000,000픽셀 변환 제한, 2048px 미디어 미리보기 및 256 MiB 디스크 캐시 제한은 유지한다.

브라우저는 기존 순차 큐 대신 최대 4개의 보이는 이미지 작업을 수행한다. 디코딩한 Image 객체 자체를 카드에 넣어 새 img를 만들며 다시 요청하던 경로를 없앴다. 별도 디코딩 이미지 캐시는 보관하지 않고 현재 DOM과 브라우저 HTTP 캐시를 이용한다. 목록은 기존 최대 60개 카드 제한을 유지한다. 실패한 아이콘을 영구적으로 실패 캐시에 보관하지 않는다.

목록 검색을 바꾸면 이전 fetch와 썸네일 대기열을 취소한다. 세대 번호와 기존 목록 요청 번호로 늦은 완료가 최신 목록을 바꾸지 못하게 한다. 이미지 한 개가 멈춰도 15초 제한 뒤 큐를 해제하며 초기화·페이지 종료 시 진행 중 작업도 정리한다. 원래 비활성화된 3D 대체 썸네일은 다시 활성화하지 않았다.

## 자동 테스트와 실제 검증

관련 자동 테스트 116개가 통과했다. 중복 재실행은 합계에 넣지 않았다.

```powershell
cd CLOSERS_Explorer
python -m unittest discover -s tests -p 'test_picker*.py'          # 6
python -m unittest discover -s tests -p 'test_preview_loading_browser.py' # 1
python -m unittest discover -s tests -p 'test_avatar*.py'          # 25
python -m unittest discover -s tests -p 'test_model*.py'           # 42
python -m unittest discover -s tests -p 'test_game_names.py'        # 5
python -m unittest discover -s tests -p 'test_local_library.py'     # 7
python -m unittest discover -s tests -p 'test_composition.py'       # 10
python -m unittest discover -s tests -p 'test_explorer.py'          # 20
```

신규 테스트는 한 연결 공유와 실제 SQL 검색 계획, A/B/C 아이콘 격리, 카탈로그 갱신과 저장 파일 삭제, 이름 검사 없는 미디어 경로, 인증·Range·304, 저장 이미지 편집·원본 변경, 동시 이미지 작업 4개 상한, 취소·실패 재시도·오래된 완료·페이지 종료, 빠른 목록 변경과 실패 시 기존 목록 보존을 검증한다. 절대 시간 임계값으로 성공을 판정하지 않는다.

재측정 도구는 프로젝트 루트에서 실행한다. 실제 results, Chrome, 로컬 서버가 필요하며 결과는 git에서 제외된 diagnostics에 저장한다.

```powershell
python CLOSERS_Explorer/tests/benchmark_avatar_picker.py local
node CLOSERS_Explorer/tests/benchmark_avatar_picker.mjs local http://127.0.0.1:8765
```

## 남은 비용과 반영

최초 캐릭터 선택에는 이름 분류와 전체 아이템 정의 캐시를 메모리에 준비하는 비용이 남아 있다. 각 목록 요청의 수천 개 원본 상태 검사도 유지하므로 페이지 조회가 즉시 끝나는 구조는 아니다. 아이템 아이콘이 없는 항목은 새 이미지를 생성하지 않고 기존 안내를 표시한다. 조건부 재검증은 네트워크 전송을 줄이지만 서버 확인 자체를 생략하지 않는다.

작업 시작 시 8765의 기존 서버와 별도 Python 프로세스를 먼저 확인했고 종료하지 않았다. 8771 비교 측정 서버를 따로 사용했다. 검증 후에는 이전 작업에서 직접 시작한 8765 서버의 현재 포트 소유자·명령·생성 시각과 작업 유휴 상태를 확인해 최종 코드로 재시작했다. 반영 후 확인한 8765 포트 소유자는 PID 28044였다. 별도 분석·추출 작업을 종료하지 않았다.
