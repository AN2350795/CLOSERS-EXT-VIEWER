# 아바타 출력 색상 경로 조사 (2026-10-30)

일반 장치 생성 경로의 설정값부터 백버퍼 RTV 생성까지 추적했다. 이 경로는 `R8G8B8A8_UNORM`(28)을 지정한다. 감마 플래그의 기본값이 켜져 있다는 사실만으로 출력 RTV가 sRGB(29)라고 판단할 수 없다. 인게임 최종 화면 전체의 감마·후처리 재현은 아직 미완료다.

## 조사 대상과 재검사

대상은 로컬 `CW.EXE`, SHA256 `8ea0ce3ba885f3044103c8e071e627b52a0e93cf56cc44b0e03dffed7c440283`이다. 실행 파일과 원본 에셋을 변경하거나 게임을 실행하지 않았다.

```powershell
python tests/audit_output_color.py --exe 'C:/Program Files (x86)/NaddicGames/Closers/CW.EXE'
```

감사 도구는 SHA256과 출력·색상 보정·프리셋·선명도 근거의 바이트 42곳을 대조한다. 코드뿐 아니라 셰이더 이름과 상수 버퍼 선택 테이블도 포함한다. 다른 버전의 실행 파일이면 주소를 적용하지 않고 실패한다. 이 검사는 기록한 근거가 그대로인지 확인하는 용도이며, 실행 중의 상태나 인게임 화면 일치를 검증하지 않는다. 선명도의 셰이더 지문과 수동 비교 범위는 [선명도 조사](AVATAR_SHARPEN.md)를 참고한다.

## 출력 Format의 연결

| 위치 | 확인한 동작 |
| --- | --- |
| `0x1417b6475` | 기본 장치 설정 `+0x28`에 Format 28 지정 |
| `0x1417b6733` | 성공한 설정 검증 경로에서도 `+0x28`에 28 지정 |
| `0x14001906e~0x140019077` | 앱이 `0x140002410`을 설정 콜백으로 등록 |
| `0x140002410~0x14000243c` | 콜백은 조건부 별도 호출 후 true 반환. 입력 설정의 Format을 쓰지 않음 |
| `0x1417bf0e7~0x1417bf180` | 콜백 호출·설정 재검증 후 로컬 설정 128바이트를 현재 상태에 복사 |
| `0x1417bc979/0x1417bc99b` | 스왑체인 descriptor Format 28, CreateSwapChain 호출 |
| `0x1417bc2d9~0x1417bc33f` | 현재 상태 `+0x28`을 RTV descriptor Format에 복사하고 CreateRenderTargetView 호출 |
| `0x1417bd1db/0x1417bd8ee` | 초기 생성·크기 변경에서 같은 RTV 생성 함수를 호출 |

RTV 생성 함수 `0x1417bc250`은 상태 `+0x497`의 감마 플래그나 형식 변환 함수 `0x1417c6790`을 직접 사용하지 않는다. 따라서 확인한 일반 생성 경로의 RTV에는 추가 하드웨어 sRGB 쓰기 변환을 지정하지 않는다. 모든 장면의 최종 출력이 이 RTV를 그대로 사용한다는 뜻으로 확대하지 않는다.

## 감마 플래그와 오탐 구분

상태 생성자 `0x1417af2bd`는 `+0x497`을 1로 초기화한다. getter `0x1417b8300`과 변환 함수 `0x1417c6790`은 별도로 존재한다. 이 변환 함수는 플래그가 켜져 있으면 28을 29로 바꾸며, 텍스처·UI 관련 경로에서 실제 호출도 확인했다. 이 사실은 아바타 백버퍼 RTV의 Format 변환 근거가 아니다.

변위 바이트 검색에서 감마 setter의 참조처럼 보였던 `0x14171f75b`는 명령 경계로 디코딩하면 `0x14171f75a: call 0x140005c40`의 일부였다. 실제 감마 setter 호출로 취급하지 않는다. 플래그가 앱에 의해 꺼진다는 근거도 확보하지 못했다. 포인터를 통한 호출 가능성 역시 직접 호출 검색만으로 배제할 수 없다.

## 후처리: 확인한 순서와 남은 연결

`NKDGDOF::m_pColorGradingRenderTarget` 이름으로 생성한 리소스는 `0x141575299~0x1415752f2`에서 객체 `+0x2a8`에 보관된다. 패스 연결 함수 `0x141575fe0`은 객체 `+0x290`의 비트에 따라 다음 호출을 수행한다.

| 순서 | 함수 | 호출 조건 |
| --- | --- | --- |
| 1 | `0x141572d60` | 연결 함수 진입 후 호출 |
| 2 | `0x1415722f0` | bit 6 |
| 3 | `0x1415716f0` | bit 2 |
| 4 | `0x141573950` | bit 4 |
| 5 | `0x141571f20` — 색상 보정 | bit 5 |

뒤 패스가 켜져 있으면 앞 패스의 출력에 중간 타깃을 사용한다. 예를 들어 bit 4와 bit 5가 함께 켜지면 네 번째 호출의 출력은 `+0x2a8`에 들어가고 색상 보정 호출의 입력으로 전달된다. `ColorGradingRenderTarget` 이름은 다음 색상 보정 패스의 입력 타깃을 가리키며, 앞 패스 자체의 셰이더 이름이 아니다.

## 색상 보정의 활성값·셰이더·상수 연결 확인

| 위치 | 확인한 연결 |
| --- | --- |
| `0x1406cb7cc~0x1406cb7de` | `ColorGrading`을 설정 객체 `+0xab`에 읽음 |
| `0x1406cb7e3~0x1406cb910` | RGB를 `+0xac/+0xb0/+0xb4`, BCS를 `+0xb8/+0xbc/+0xc0`에 읽음 |
| `0x1406d4eb2~0x1406d4f24` | 활성 설정에서 bit 5를 지정하고 RGB 다음 BCS 순서의 벡터를 후처리 객체 `+0x2f0`에 전달 |
| `0x141576132~0x141576158` | bit 5일 때 마지막 패스 함수 `0x141571f20` 호출 |
| `0x141571fbf~0x141571fc4` | 기법 번호 `0x10` 선택 |
| `0x1416069d4~0x141606c12` | 후처리 효과에 PS 16개를 순서대로 등록. 마지막 16번이 `CW_ColorGrading.PS.cso` |
| `0x1415fcc87~0x1415fccc1` | 기법 번호에서 1을 빼 PS 목록 인덱스로 사용. 따라서 기법 16은 위 마지막 PS 선택 |
| `0x141674a56~0x141674b21` | bit 5에서 설정 벡터를 읽어 색상 보정 상수 작성 |
| `0x141602527/0x141602670` | 상수 원본 포인터 테이블의 해당 선택이 `0x142fb6610`을 가리킴 |

설정 적용 경로는 여러 개다. `0x1406d5364~0x1406d53c2`에서는 별도 시스템 설정 `+0x183`으로 bit 5를 지정한 후 색상 설정 객체의 RGB·BCS를 전달한다. 따라서 특정 파일의 `ColorGrading` 필드 하나만 읽어 모든 장면에서 켜진다고 판단하면 안 된다.

상수 작성 함수의 기본값과 실제 입력 순서를 구분했다. 색상 보정 데이터가 비어 있으면 첫 float4는 `(0,0,1,0)`, 두 번째는 `(1,1,1,0)`이다. 데이터가 있으면 다음과 같이 채운다.

| 셰이더 상수 | CPU 주소 | 값 |
| --- | --- | --- |
| `cb6[28].x` | `0x142fb67d0` | 항상 0 — 이 경로에서 추가 노출을 지정하지 않음 |
| `cb6[28].y` | `0x142fb67d4` | BCS.y — 대비 |
| `cb6[28].z` | `0x142fb67d8` | BCS.z — 채도 |
| `cb6[28].w` | `0x142fb67dc` | BCS.x — 밝기 |
| `cb6[29].rgb` | `0x142fb67e0~0x142fb67e8` | RGB 배율 |

색상 보정 상수의 시작은 CPU 버퍼 `0x142fb6610`에서 448바이트 뒤이며, 원본 PS의 `CBPerPostProcess.g_v4ColorGradingValue[2]` 오프셋과 일치한다. 셰이더는 노출 0에서 다음 계산을 수행한다. `C`는 앞 패스가 출력한 RGB 값이다.

```text
contrast = max(1 + BCS.y, 0)
tinted = ((C + BCS.x - 0.5) * contrast + 0.5) * RGB
luma = dot(tinted, (0.2125, 0.7154, 0.0721))
output.rgb = clamp(luma + BCS.z * (tinted - luma), 0, 1)
output.a = clamp(input.a, 0, 1)
```

빈 데이터 기본값은 위 식에서 색을 그대로 통과시킨다(출력 범위 제한 제외). 밝기를 대비 계산 뒤에 더하거나, RGB 배율 적용 전에 채도를 계산하는 구현은 원본과 다르다. 이 PS 자체에는 sRGB 감마 변환이나 필름형 톤 매핑이 없다. 이후 다른 출력 경로가 없는지까지 증명한 것은 아니다.

로컬 `GAME_OPTION.lua`에는 RGB `(1,1,1.1)`, BCS `(0,0.05,1.3)`, `PostEffectPreset=5`가 기록되어 있다. 이는 조사 PC의 저장 설정이며 모든 사용자·장면의 기본값이 아니다. 해당 파일에는 명시적 `ColorGrading` 활성 필드가 없으므로 프리셋·시스템 설정 적용까지 확인하지 않고 자동 적용하지 않는다. 원본 파일은 읽기만 했고 전체 사용자 설정을 감사 결과에 복사하지 않았다.

## 뷰어 반영 범위와 다음 작업

그래픽 프리셋 적용 함수 `0x140092700`도 연결했다. `0x1406cc530`은 범주 5에서 요청한 프리셋 ID를 찾는다. 로더 `0x1406dcfe0`은 `GRAPHIC_OPTION_DATA_DETAIL.NTF`의 숫자 열 5~14를 구조체 `+0x5c`부터 연속으로 읽는다(`0x1406dd4dd` 부근). 적용 함수는 첫 두 값을 지나 `+0x64`부터 여섯 색상 값을 읽고, 범주 3의 각 채널 최소·최대와 비교한다. 유효한 값 중 양수의 개수를 세어 `0x140092a11~0x140092a70`에서 활성 여부와 RGB·BCS를 설정 객체에 기록한다.

| 프리셋 ID | RGB | 밝기·대비·채도 | 원본 적용 시 색상 활성 |
| --- | --- | --- | --- |
| 1 | 1.2, 0.95, 0.85 | 0, -0.2, 1 | 켜짐 |
| 2 | 1.2, 1, 1 | 0.05, 0, 1.3 | 켜짐 |
| 3 | 0.85, 0.75, 0.75 | 0.08, 0, 1 | 켜짐 |
| 4 | 1, 1, 1 | 0, 0, 0 | 켜짐 — 무채색 |
| 5 | 1, 1, 1.1 | 0, 0.05, 1.3 | 켜짐 |
| 6 | 1.05, 1, 1 | 0, 0, 1.8 | 켜짐 |
| 7 | 1.05, 1.05, 1.05 | 0.1, -0.05, 1.5 | 켜짐 |

표는 읽기 좋게 반올림한 값이다. API는 원본 float32를 보존하며 프리셋마다 원본 행과 SHA256을 제공한다. 이 범주에서 RGB 범위는 0~2, 밝기·대비는 -1~1, 채도는 0~2다. 위 ID 5는 조사 PC의 저장 수치와 일치하지만, 저장 수치만으로 공통 기본값을 정한 것은 아니다. 이 적용 경로의 활성 규칙은 여섯 값 전체를 대상으로 하므로 채도가 0인 ID 4도 활성이다. 범위를 벗어나는 자료는 뷰어가 추정하거나 clamp하여 프리셋으로 제공하지 않는다.

현재 **원본 형식의 색상 계산 비교 (후처리 미포함)**는 입력 UNORM 계산과 추가 sRGB 출력 변환 생략을 함께 비교한다. 이번 조사로 일반 RTV 생성 경로에 대한 근거를 보강했다. 기본은 계속 OFF이며 인게임 재현 옵션으로 이름을 바꾸지 않는다.

색상 보정의 활성 비트·기법·셰이더·상수·공통 프리셋 연결을 수동 비교에 연결했다. 프리셋 적용은 보정 켜짐과 다른 효과를 바꾸지 않는다. 첫 적용 전 직접 입력값을 별도로 보존하고 수치를 저장한다. 발광만 보기와 광택 마스크 진단은 보류한다. 후속 단계에서 [그래픽 옵션 프리셋과 지역 화면 효과의 구분](AVATAR_SCENE_POSTPROCESS.md)을 확인하고 비색상 후처리의 원본 구성 표시를 추가했다. 감사 근거는 32곳이다. 장면별 덮어쓰기·실시간 선택과 다른 후처리의 렌더링은 남아 있으며, 동일 조건 인게임 대조 없이 기본 계산을 변경하지 않는다.
